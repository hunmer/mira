## 根本原因

`customFields.enableHash` 开启后上传新文件没有进行 hash 验证，有两层问题：

1. **配置失效（主因）**：`enableHash` 在 `LibraryServerDataSQLite` 构造函数里被快照成 `readonly` 字段（`LibraryServerDataSQLite.ts:21`）。仪表盘切换开关走的是 PUT `/:id`，它只重新赋值了 `libraryService.config = updatedConfig`（`LibraryRoutes.ts:251`），**没有**重建实例，也没刷新 `enableHash`。而 `FileImport.ts:17` 判断的是 `this.enableHash`（过期快照），所以永远是 `false` → `hash` 算成空串。只有在库被禁用/启用或服务器重启后才生效。

2. **缺少去重逻辑**：即便 hash 被正确计算，代码里也**没有任何**按 hash 查重的逻辑 —— hash 只被存库（以及用作缩略图文件名），从没拿去和现有文件比对。所以"哈希校验"实际上什么都没校验。

## 修复方案（用户已确认：跳过重复 + 改成 getter）

### 文件 1：`packages/mira-app-core/src/storage/sqlite/LibraryServerDataSQLite.ts`
把快照字段改成实时 getter，让开关切换立即生效：
- 删除字段声明 `readonly enableHash: boolean;` 与 `readonly customFields: Record<string, any>;`
- 删除构造函数中的 `this.customFields = ...` 和 `this.enableHash = ...`
- 新增两个 getter，从当前 config 读取：
```ts
get enableHash(): boolean {
  return this.config.customFields?.enableHash ?? false;
}
get customFields(): Record<string, any> {
  return this.config.customFields || {};
}
```
- 这样 `LibraryRoutes.ts:251` 重新赋值 `config` 后，下一次读取 `this.enableHash` 立即拿到新值。接口里的 `readonly enableHash` / `customFields?` 声明（`ILibraryServerData.ts`、`mixins/types.ts`）由 getter 自动满足，无需改动。

### 文件 2：`packages/mira-app-core/src/storage/sqlite/mixins/FileImport.ts`
在 `createFileFromPath` 里、计算完 hash 之后、调用 `handleFile`/`createFile` 之前，加入查重：
```ts
const hash = this.enableHash ? this.calculateFileHashSync(filePath) : '';

// hash 去重：库中已存在相同 hash 的文件则跳过导入
if (hash) {
  const existing = await this.getSql(
    'SELECT * FROM files WHERE hash = ? AND recycled = 0 LIMIT 1',
    [hash]
  );
  if (existing.length > 0) {
    // move 方式导入时清理临时源文件，避免残留（上传走的就是 move）
    if ((options?.importType || 'copy') === 'move') {
      try { fs.unlinkSync(filePath); } catch {}
    }
    return { ...this.rowToMap(existing[0]), duplicate: true };
  }
}
```
- 命中重复时跳过复制/移动与入库，返回已存在记录并打 `duplicate: true` 标记（向后兼容，其他 4 个调用方不受影响）。
- hash 为空（开关关闭）时完全不触发查重，行为不变。
- 只查 `recycled = 0` 的活动文件（回收站里的不算重复）。

### 文件 3：`packages/mira-app-server/src/routes/FileRoutes.ts`
上传路由的 create 分支识别 `duplicate` 标记并如实上报：
```ts
result = await obj.libraryService.createFileFromPath(file.path, fileData, { importType: 'move' });
const isDuplicate = result?.duplicate === true;
results.push({
  success: !isDuplicate,
  file: file.path,
  result,
  operation: isDuplicate ? 'duplicate' : 'create'
});

// 命中重复时不广播 file::created（没有新建），仅向上传方回传已处理
if (this.backend.webSocketServer && !isDuplicate) {
  // ... 原 file::created 广播逻辑 ...
}
if (this.backend.webSocketServer && clientId) {
  const ws = ...;
  ws && this.backend.webSocketServer?.sendToWebsocket(ws, {
    eventName: 'file::uploaded',
    data: { path: sourcePath, ...(isDuplicate ? { duplicate: true } : {}) }
  });
}
```

## 不改动 / 已评估
- `FileHandler.ts`（WS `create` 路径）：复用同一 `createFileFromPath`，重复时返回的是带标记的已存在记录，向后兼容，无需强制改动。
- `calculateFileHashSync` 现有实现（读文件取前 32 hex）保持不变 —— 本次只修"是否生效 + 是否查重"，不改算法。
- 不触碰 `LibraryRoutes.ts` 现有 config 重赋值逻辑（getter 已让它生效）。

## 验证

- 再次上传同一文件 → 确认返回 `operation: 'duplicate'`、`success: false`，库里不产生新记录，临时文件被清理。
- 关闭 `enableHash` 后上传同一文件 → 确认不查重、正常入库（与历史行为一致）。
